# DOX: src/ -- Core Hound ELINT Source

## Purpose

Implement the Hound ELINT DCS World mod: radar emitter detection, triangulation, tracking, map markers, voice comms (ATIS/Controller/Notifier), sector management, and data export.

### Runtime Constraints

Runs in DCS sandbox (Lua 5.1): no `require`, no `io.*`/`os.*` (except `os.time`/`os.date`). All APIs are DCS globals (`timer`, `coalition`, `Unit`, `world`, `env`).

## Ownership

This subtree owns all Lua source files that compose the HoundElint system. The normal build artifact is `include/HoundElint.lua`, assembled from these sources by `hound_builder.sh`. An optional minified build `include/minified/HoundElint_.lua` is produced with `hound_builder.sh --minify`.

## Local Contracts

- **Numbered loading order**: 36 files prefixed `NNN -` loaded sequentially by `HoundElint_devel.lua`. The numbering establishes dependency order (lower = loaded first).
- **File groups by number range**:
  - `000-099`: Globals, Logger, Coroutine, Mist shim, Matrix math
  - `100-199`: Databases (DCS units, mods, config)
  - `200-299`: Utilities, TTS, Event Handler
  - `300-399`: Contact model (Base, Estimator, Datapoint, Emitter, Site, plus _comms variants)
  - `400-499`: Comms (Manager, InformationSystem, Controller, Notifier)
  - `500-599`: Worker, ContactManager, Sector, Sector menu
  - `800-899`: HoundElint main entry point and subsystems
  - `999`: Footer (post-init cleanup)
- **No cross-file circular dependencies** at require/load level; all cross-references go through the global `HOUND` namespace table.
- **All public API** is documented via LDoc annotations and extracted by `tools/generate_md_docs.py`.
- **Single global**: The `HOUND` table. Everything else is local or nested under `HOUND`.

### Data Model

- `HOUND.ElintWorker.contacts[unitName] = Emitter` — master list of detected radar emitters
- `HOUND.ElintWorker.sites[groupId] = Site` — logical grouping by DCS Group
- `Site.emitters[]` are **references** into `contacts`, not copies
- `Site.last_seen` stores the emitter's **absolute** `getAbsTime()` timestamp (never a relative age)
- `HOUND.DB.HumanUnits` entries are regenerated by `updateHumanDb` on every menu rebuild (60s) and pruned by `cleanHumanDb` in the same rebuild once `lastSeen` is older than 300s. `HoundElint:populateRadioMenu` calls both in that order, so a connected player is always refreshed before the purge runs. Entries can be recreated at any time from `coalition.getPlayers`.
- `Site.typeAssigned` computed by **set intersection** of its emitters' `typeAssigned` arrays
- `Contact.Base` position data (`pos.LL`, `pos.grid`, `pos.be`, `_hexCell`) is lazily derived from `pos.p`; `hasPosData()`/`ensurePosData()` gate functions that concatenate grid/BE strings
- `ensurePosData()` recomputes `pos.LL` from `pos.p` when either `lat` or `lon` is absent (partial LL values are not trusted)

### Processing Cycles (default intervals)

| Cycle | Interval | Detail |
|-------|----------|--------|
| Scan | 10s | Coroutine, discovery yields every 128 groups |
| Process | 30s | Per-emitter: Kalman fast path or triangulate datapoints |
| Menu | 60s | Atomic F10 radio menu rebuild, sorted by distance |
| Markers | 120s | Coroutine, yields every 3 sites |
| ATIS | 180s | Refresh broadcast text (transmission scheduler 4s) |
| Launch cooldown | `AlertOnLaunchCooldown` (30s) | Per-site independent counter. Suppresses all launch handling while a site is inside its window |

Coroutine scheduler pump interval: **50ms** (`src/011 - HoundCoroutine.lua`).

### Launch Event Gate

`S_EVENT_SHOT` handling in `804 - HoundElintEvents.lua` gates in order, cheapest first. Do not reorder or move work above a gate:

1. `HOUND.Utils.Dcs.isUnitAlive(DcsEvent.initiator)` - every later gate dereferences the initiator; a unit destroyed between the event and the slice raises on `getCoalition` / `getGroup`
2. Ground/ship + enemy coalition + `Air Defence` attribute
3. `HOUND.Utils.Dcs.isRadarGuidedMissile` - rejects shells, rockets, bombs, and TV/IR/laser/INS/TELE guided missiles. AAA barrages produce orders of magnitude more `S_EVENT_SHOT` events than missile salvos
4. `HOUND.Utils.Dcs.isGroupAlive(grp)`
5. `HOUND.ElintWorker:onLaunchCooldown(grpName)` - per-site independent counter (`Site.last_launch_processed`). **Must not use `last_seen`**: a normal scan sample would refresh it and permanently suppress launch handling

Gate 5 exits the whole block - `Sniff`, `ensureSitePrimaryHasPos` and `AlertOnLaunch` all skip. Unknown groups are never on cooldown, they are not tracked yet. The first launch of an unknown group creates its site inside `Sniff`; the handler stamps `last_launch_processed` on that new site afterwards, so the rest of the salvo hits gate 5 instead of being processed again.

### Emitter State Machine

`NEW → DETECTED|UPDATED → ASLEEP (15 min idle) → SITE_ALIVE → UPDATED`, plus `DESTROYED`.

### Runtime Performance Contract

DCS runs all mission scripting on one thread. Every hook (event handler, timer callback, coroutine step) blocks the simulation while it runs. Cost per tick must scale with the work actually needed, not with total mission size.

- **Guard once, at the boundary.** Validate at the public entry point or where a DCS handle enters the system. Inner functions trust their contract; no stacked `nil`/type/liveness checks on values the caller already validated.
- **No speculative guards.** Do not add a check for a state the contract excludes ("just in case"). A guard that runs per contact per tick costs every mission; a missing guard costs one stack trace.
- **No repeated tests in one call path.** Do not test the same handle, name, or flag at consecutive layers (caller tests, callee tests again). Do not test a condition and then re-test it inline in the same block.
- **Hoist invariants out of loops.** Resolve DCS handles, names, config values, `contacts[x]`/`sites[x]` lookups, and `getmetatable` checks once before the loop, never per iteration.
- **Never re-derive cached data.** `hasPosData()`/`ensurePosData()` own `pos.LL`/`pos.grid`/`pos.be`; consumers read the cached value instead of recomputing strings per contact per tick.
- **Event-driven over poll.** Do work in the event or state transition that changes the data, not in a timer that re-derives it. Existing cycles (Scan 10s, Process 30s, Menu 60s, Markers 120s) are budgets, not targets.
- **Cheapest reject first.** Never move expensive work above a cheap gate (see Launch Event Gate).
- **Yield long walks.** Any walk over contacts, sites, or groups goes through `HOUND.Coroutine` in batches (Scan yields every 128 groups, Markers every 3 sites). No new unbounded loop on the main thread. Pump interval 50ms, per-resume budget `MaxExecutionTime = 0.01`.
- **No per-tick allocation in hot paths.** Reuse scratch tables and locals; build strings only at the point they are consumed (marker text, menu text, exports).
- **Prefer inline handling over pre-check + call.** One `if` that handles the absent case where it is used beats a separate validation pass that walks the same data first.

### Sector Zone Hex Grid

- `HOUND.useHexGrid` (default true) selects the hex query; set it false to restore the legacy polygon path (`pointInPolygon` + `shape.insideShape`) for rollback or the DCS agreement run.
- `HOUND.hexRadius` (default 1000 m) is the single resolution. `HOUND.setHexRadius` and `HOUND.Mist.hex.setRadius` reject non-numbers and values below 1; the global setter resets every zoned sector's classification cache via `Sector:setZone(zone)`.
- Ownership: the contact owns "which cell am I in" (`Contact.Base:getHexCell`, derived from `pos.p` and cached with the hex radius, next to `pos.LL`/`grid`/`be`); the sector owns "what this cell means for my zone" (`sector._zoneHexCache`). Neither caches the other's answer.
- `HOUND.Sector:setZone` is synchronous: it stores the zone, `zoneCenter`, `_zonePoly = {xs, zs, n}` (flat edge coordinate arrays) and an empty `_zoneHexCache`. No zone-wide cell set is built. A string candidate is resolved as drawn zone then group route; `nil` triggers the implicit lookup for the `<sector name> Sector` drawn zone. An unresolved or invalid candidate (fewer than 3 points, non-point entries, non-array or sparse tables) leaves the current zone, `zoneCenter`, `_zonePoly` and `_zoneHexCache` unchanged; both Vec2 `{x,y}` drawn zones and Vec3 `{x,y,z}` group routes are accepted. `HoundElint:setZone` accepts a string or `nil` and delegates here. The optional `onComplete` callback runs synchronously at the end. `removeZone` clears zone, center, `_zonePoly`, `_zoneHexCache`. `Sector:updateSettings({zone = ...})` delegates to `setZone`: a valid replacement resets the cache, an invalid one leaves the current zone and cache unchanged.
- `HOUND.Utils.Polygon.zoneDistance(px, pz, xs, zs, n)` is a single pass: even-odd inside test plus minimum segment distance. It returns `(inside, distance)` with distance 0 inside.
- `HOUND.Utils.Polygon.threatOnSector(polygon, point, radius, hexPoint, hexCache, zonePoly)` returns `(inSector, intersectsZone)`. It returns nil when `zonePoly` or `hexCache` is absent (default and meta sectors). `hexPoint` is optional; without it the function derives the cell from `point` and validates the point. With a cell it classifies lazily on first sight: one `zoneDistance` per `hex.cellKey`, cached `{inside, distance, radius}`. An entry computed at a different radius is recomputed, so a direct `HOUND.Mist.hex.setRadius` cannot leave stale cell geometry behind. `inSector = inside`; `intersects = distance <= radius + hexRadius`, so a threat is never missed and the range is re-evaluated per call without recomputing geometry. Set `HOUND.useHexGrid = false` to route to `threatOnSectorLegacy` instead.
- `HoundElint:updateSectorMembership` snapshots the name-keyed `contacts`/`sites` dictionaries into arrays in one non-yielding pass (a plain table copy; the live dicts must not gain keys between `pairs` resumes — undefined behaviour in Lua 5.1), then iterates the snapshots with `ipairs`. New contacts/sites created during the yielding walk are handled by the `_sectorUpdateQueued` requeue. Each `Sector:updateSectorMembership(contact)` reads `contact:getHexCell()` and the sector cache; the walk yields every 128 processed items and once at the end of each sector, and the site walk yields every 128 sites, so no unbounded work loop runs on the main thread. A radius change between sectors is handled by `getHexCell` (it compares the stored radius), so no per-cycle hex snapshot is shared or rebuilt.
- `HOUND.Contact.Base:isThreatening` excludes the sector member (`primarySector`); `threatSectors` remains the single membership store.
- `HOUND.Mist.hex.getFromRoute` (edge plus fill, optional `yieldFn`) is a hex helper only; sector zones do not use it.

### Key Conventions

- New files go between existing numeric prefixes (e.g. `115 - Foo.lua` after `110`)
- Don't gate production logic on `HOUND.DEBUG` — compile flips it to `false`
- Don't put logic in `StopWatch` / `:Stop()` / `HOUND.Logger.trace("` lines — stripped at compile
- `HOUND.Coroutine` is pump-safe: `add` may append to `_list` during a pump and the new record runs on a later tick, while `cancel`/`cancelByName`/`shutdown` mark records dead (`rec.dead`) instead of removing them; dead records are purged after the walk (`purgeDead`). Never remove from or reorder `_list` from inside a coroutine body or its callbacks. New records use `lastResume = -math.huge` so the first pump slice is due immediately; do not initialize it from `now - interval` (floating-point rounding at large mission times skips the first slice)
- `HOUND.Matrix:new` and `HOUND.Contact.Estimator.UPLKF:create` are methods. Their `__call` metamethods (`matrix(...)`, `UPLKF(...)`) must re-supply the receiver (`HOUND.Matrix:new(...)`, `.create(...)`); dropping the implicit call argument passes the first user argument as `self` and fails at runtime
- `Sector:setCallsign` releases the sector's own pool registration before the availability check, so re-applying the current callsign keeps it; only foreign registrations force a new callsign
- `DATAPOINTS_NUM = 30` hard FIFO cap per platform per emitter
- `S_EVENT_WEAPON_ADD`: payload name comes from `DcsEvent.weapon:getTypeName()` (guarded by `isExist()`); DCS no longer fills `weapon_name`
- `Controller:getDetectedTargets()` returns `DetectedTarget` descriptors (`{object=..., visible=...}`), not object handles; read `.object` before liveness/method calls
- Pre-briefed contacts (`preBriefedContact`) bypass triangulation but still drive state machine
- Validate DCS handles before method calls: `coalition.getGroups` / `coalition.getStaticObjects` / `Group.getByName` return objects that may already be destroyed, and a live group can still hold destroyed units. DCS raises on any method call for a dead handle. Use `HOUND.Utils.Dcs.isGroupAlive` / `isUnitAlive` / `isStaticObjectAlive` / `getGroupUnits` (defined in `200 - HoundUtils.lua`) before calling methods on a handle. `isGroup` / `isUnit` / `isStaticObject` are type tests only — keep them where liveness is irrelevant or where a distinct dead state is part of the contract (`HOUND.Utils.TTS.getTransmitterPos`, `HOUND.Contact.Emitter:isAlive()`, the `S_EVENT_UNIT_LOST` gate in `804 - HoundElintEvents.lua`, the unit branch of `markDeadContact` in `801 - HoundElint_properties.lua`).
